# FD012 — The pull_request context is accepted

**Severity:** high.

## What it means

The subject accepts the `pull_request` context:

```
repo:acme/api:pull_request
```

That is the subject a **`pull_request_target`** workflow runs under. Those
workflows execute in the context of the base repository, with its secrets and
its permissions, while operating on code from the pull request.

## Why this is not the usual "forks are safe" case

For an ordinary `pull_request` event from a fork, GitHub grants a read-only
token and does not issue an OIDC token with `id-token: write`. That is the part
people remember, and it is true.

`pull_request_target` is the exception, and it exists precisely because
maintainers wanted base-repository permissions on fork contributions. A workflow
that checks out `github.event.pull_request.head.sha` and then runs anything
from it — a build script, a lint config, a `package.json` lifecycle hook — is
running attacker-supplied code with your credentials.

## What an attacker does

Opens a pull request. Nothing else. No write access, no account in your
organization, no review.

## How to fix it

1. **Audit every `pull_request_target` workflow in the repository** for a
   checkout of untrusted code. This is the actual fix; the trust policy is the
   second half.

2. **Move deployment credentials off that path.** A role reachable from a pull
   request should not also be the role that deploys:

   ```jsonc
   "StringEquals": {
     "token.actions.githubusercontent.com:sub": "repo:acme/api:environment:production"
   }
   ```

3. If a PR workflow genuinely needs cloud access — to run integration tests,
   say — give it a separate role with read-only permissions scoped to a test
   account, and leave this finding suppressed against that role with the
   reason written down.
